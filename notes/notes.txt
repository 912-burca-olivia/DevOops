------ HOW TO TEST YOUR CODE ------

1. use debugging to test:

- install delve (debugging for go): go install github.com/go-delve/delve/cmd/dlv@latest
- check that you have it: dlv version
- now in VSCode open the itu-minitwit folder
- add a file named "launch.json"
- copy paste this code in that file:
{
    "version": "0.2.0",
    "configurations": [
      {
        "name": "Launch",
        "type": "go",
        "request": "launch",
        "mode": "debug",
        "program": "${workspaceFolder}",
        "env": {},
        "args": []
      }
    ]
  }
  
From now on you can test the api methods by putting breakpoints there
And start the debugger by pressing F5 key from the minitwit-api.go file
(the minitwit-api docker container should be stopped
while the minitwit-app docker container should be started)

example: I want to test the login endpoint from the API
Since LoginHandler from the minitwit app uses my endpoint for the login
I will go to localhost:8080/login to check (this works because the app is started)
And I will then debug PostLoginHandler method from the minitwit api (I can debug it because I stopped the api container and now the port 9090 is available)

2. how to check/modify the database in the docker container:
- start the minitwit api container
- use command: docker exec -it minitwit_api sh
- install sqlite3 in the container if you do not have it:
apt-get update
apt install sqlite3
- go in the database: sqlite3 minitwit.db
- example command to check the tables: .tables

 ------ DATABASE MIGRATION ISSUES ------

1. kept getting connection refused

how to solve it:

db droplet on digital ocean -> trusted sources -> add ip of laptop to trusted sources for pgload command

download ca certificate from digital ocean and: 

 sudo cp ca-certificate.crt /usr/local/share/ca-certificates/
 sudo update-ca-certificates
 
2. sqlite gorm stores boolean as numerical (0 or 1) -> issues when migrating to postgres using pgloader.

how to solve it: 

tried to use a pgloader script and use casting but found out in pgloader documentation that it cannot be done for a specific column, only for casting all columns of the same type.
so, manually changed type of 'flagged' column from bool to uint for pgloader to work and also changed the code in the project accordingly

3. db password would be exposed in docker compose file

how to solve it:

put db connection details in an .env file in the remote server only; putting the db connection details on git is not a good idea since it will expose the password

4. after pushing all modifications, app & api stopped working, the connection to the db was failing. because of too many connections (1 / each request). (error: [error] failed to initialize database, got error failed to connect to host=minitwit-db-do-user-19242632-0.g.db.ondigitalocean.com user=doadmin database=defaultdb: server error (FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute (SQLSTATE 53300)) )

how to solve it:

make the api connect only once to the db, not for each request. 


------ FAILOVER STRATEGY ISSUES ------

hot and standby server

- created a snapshot of first server in order to make a copy of it (as the second server)
- add a reserved(floating) IP to the first droplet/server
- install keepalived on both servers/droplets
- configure keepalived for both servers
- created new token 'DO_TOKEN' in digital ocean
- issue: python script was not working -> modified master.sh script to use python3
- allow necessary connection to the db on digital ocean
- created scripts (all of them must be executable):
	1. /usr/local/bin/check-api.sh: checks if the application is running. If it fails, Keepalived will trigger a failover
	2. /etc/keepalived/master.sh: assigns the floating IP to the active droplet when a failover happens
	3. /etc/keepalived/keepalived.conf: defines how Keepalived will manage failover between primary and backup servers
	4. /etc/systemd/system/keepalived.service: starts keepalived using systemd instead of Upstart (this is needed because we are using a modern version of ubuntu)

How does everything work?
1. Keepalived is started and runs on both droplets
2. The primary droplet (default) holds the floating IP (67.207.75.4)
3. If the primary droplet fails (api stops running):
 - The secondary droplet (default2) detects failure (via check-api.sh)
 - The secondary droplet takes over (master.sh assigns the floating IP to this droplet)
4. Traffic continues without downtime
